# Phase 07 — Install into a project (optional)

Inputs: a QA-passed `<brand>-skill/` (phase 06 signed off) and a target project directory.
Run this phase only when the user wants the skill wired into a project; a standalone skill
handoff ends at phase 06.

Ask (or confirm from context) the target project path. Any project with a web front end is a
valid target. Before copying anything, look: find its stylesheet entry point and how CSS
reaches the page, and check for an existing `.claude/skills/`, `.pi/settings.json` and
agent-instructions file (`AGENTS.md`, `CLAUDE.md`). Report what you found and what you
intend to change, and wait for a yes — every edit below lands in files the user owns.

## What "installed" means

Three things, all idempotent (re-running after a rebrand overwrites the generated pieces
and touches nothing human-owned):

### 1. The skill, discoverable by agents

Copy the entire `<brand>-skill/` to `<project>/.claude/skills/<brand>-design-skill/`. The
destination directory matches the generated skill's frontmatter `name`. Do not prune the
`site/` directory — it is the visual reference.

Present on disk is not discoverable. Claude Code loads project skills from `.claude/skills/`;
pi does not. pi's project locations are `.pi/skills/` and `.agents/skills/` (see pi's
`docs/skills.md`, "Locations"), and it reads them only after the project is trusted. For pi,
do one of these and say which:

- **Register the folder** (preferred — one copy serves both agents): make sure
  `<project>/.pi/settings.json` has `"skills": ["../.claude/skills"]`. Paths in that file
  resolve relative to `.pi/`, so `../.claude/skills` is the project's `.claude/skills/`.
  Add to an existing `skills` array; never replace it or touch any other key.
- **Or copy into `.pi/skills/<brand>-design-skill/`** — only if the user wants no settings
  change. It is then a second copy, and a rebrand must re-install both.

Never assume a folder is scanned because its name looks conventional: `.claude/skills/`
reaches pi through the settings entry and nothing else.

### 2. The CSS, loaded by the page

The skill ships two stylesheets and no build step: `tokens.css` (custom properties,
`@font-face`, element defaults) and `<brand>.css` (components, consuming only tokens).
**Tokens load first, always.** Copy both into the project's own styles directory under
`brand/`, and prepend to each copy:

```css
/* GENERATED by brandmaker from .claude/skills/<brand>-design-skill/ — DO NOT EDIT.
   To change the brand: edit the skill (or re-run brandmaker), then re-install. */
```

Then wire them in the way the project already loads CSS — never add a pipeline it lacks:

- **SASS**: copy as `brand/_tokens.scss` and `brand/_components.scss` (plain CSS is valid
  SCSS) and add `@use 'brand/tokens';` then `@use 'brand/components';` at the top of the
  entry stylesheet.
- **PostCSS / a bundler that resolves `@import`** (Vite, webpack, etc.): copy as
  `brand/tokens.css` and `brand/components.css` and add `@import './brand/tokens.css';`
  then `@import './brand/components.css';` at the top of the entry stylesheet, or import
  both from the JS entry in that order.
- **No pipeline**: copy as above and link both from the HTML `<head>`, tokens first, before
  any existing stylesheet.

Add those two lines, if missing, and never duplicate them. The entry stylesheet stays
human-owned: never reorder or remove anything else in it. Hand-written styles layer on top
by consuming the custom properties (`var(--clr-…)`, `var(--space-…)`) — never by
redefining them.

### 3. The pointer that gets it used

An installed skill nobody routes to is decoration. With the user's yes, add one short entry
to the project's agent-instructions file (`AGENTS.md`, `CLAUDE.md`, or the equivalent they
name): the skill's path, that it is the source of truth for any UI or styling work, and
that the `brand/` copies are generated. If the project keeps its conventions elsewhere, put
it there instead. Create no such file unasked — offer the text and let the user place it.

### Assets

- Fonts: copy `fonts/` to wherever the project serves static files, under `fonts/<brand>/`,
  and rewrite the `@font-face` `url()` paths in the *copied* tokens file to match. The skill
  copy keeps its relative paths (it must stay self-contained).
- Logos/icons: copy `assets/` to the project's static directory under `img/brand/`. Tell
  the user the paths so they can reference them from views.

## Source of truth

The skill directory (`.claude/skills/<brand>-design-skill/`) is canonical. The `brand/`
stylesheets and the static fonts and images are generated copies. A rebrand is: edit the
skill (or re-run brandmaker phases as needed) → re-run this phase.

## Verification before declaring done

1. The project's build (or one cycle of its watcher) succeeds with the brand CSS included;
   with no pipeline, the page loads both files with no 404.
2. Open the app (or a rendered page) and confirm base elements pick up the brand: body
   font, link color, heading scale. A page that still shows browser defaults means the
   import didn't land or load order is wrong (tokens must load first).
3. Check the network/console for 404s on font files — the most common install failure is
   an unrewritten `@font-face` path.
4. Confirm discovery rather than infer it: in a fresh pi session in the project, the skill
   appears in the available skills (or `/skill:<brand>-design-skill` loads it).
5. Report to the user: what was copied where, every line added to which file (entry
   stylesheet, `.pi/settings.json`, instructions file), and the rebrand procedure.
