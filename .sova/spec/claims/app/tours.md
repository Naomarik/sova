# §app/tours — Guided tours

A guided tour explains a real interface or UI experiment through recorded pictures and short explanations, organized as chapters, main steps and named views. The user requests it in chat; the agent prepares, records and checks it with Sova's tools before presenting it. Viewing a message never starts a recording. Record, view, share and organization hand-off delivery are available together.

## §app.tours/authoring — Explain an interface with the tour tools

The vis toolset's table of contents includes `tour`, distinct from the pure drawing-fence kinds. `vis_guide` with `tour` teaches when a recorded tour helps more than a wireframe or interactive illustration and returns the core of the authoring and recording workflow; there is no executable `vis tour` fence. The rare cases are four parts the core names, each returned alone by `vis_guide` with its name: `tour-signin` (the sign-in in full: login in the request or on the card, the login's shape with its account, re-sign-in, held sessions, sign-in notices, signed-in editions kept out of sharing, stored test accounts), `tour-sites` (sources, site approval and Approve All, the sandbox, the recorder's network rules, live, local and dev servers), `tour-sova` (recording Sova itself on a test copy) and `tour-sharing` (share links, hand-offs, published editions). The parts are lookups, never catalogue kinds; the catalogue's `tour` line names them in a few words, and recorder messages that need one cite it by that name. Each rule of the guide lives in exactly one of these files. The agent uses Sova's harness-neutral `record_tour` and `show_tour` tools in both ordinary pi-backed and Sova Claude Code chats, not a browser hidden in a markdown renderer. In ordinary chats these two tools require the vis minor mode to be on; align's Visuals alone does not grant them, although `vis_guide` and `vis_check` retain their existing align-Visuals availability. A hand-off's scoped presentation-only `show_tour` remains baseline conversation context. `record_tour`'s own description, which the agent always has, carries the rules behind most failed dry runs in one line: each picture is one screen (desktop 1440×960, phone 390×844), every target matches exactly one visible control, an accessible role and name comes first, the tour's id goes beside the script and never inside it, and status waits for the job to rest or need the user (up to five minutes), so the agent never sleeps or polls in a loop; its `credentials` description shows the full login shape, account included.

Before recording, the guide tells the agent to establish the audience, what to cover, the UI experiment or comparison, and what the reader should understand or decide; discover the authorized source and sites; use seeded data, a test account, or an account the user chooses to sign in with (§app.tours/sites); identify private regions; and organize chapters around tasks with one outcome per main step. Titles and explanations say why a view matters and what to notice next. Named views cover alternatives or before/after comparisons without changing the main-step sequence. Desktop and phone actions and useful callouts are specified deliberately, not guessed from one another. The guide tells the agent to write reference text as short paragraphs separated by blank lines, one per part (what the state is, what the reader would see, why it isn't pictured), because the viewer shows it as written.

The core is short (at most 13,500 characters, about 3,000 tokens, read once and then carried by the chat) and written for a cheap model: short lines, numbered rules, the must-know first. It covers the ordinary case alone (a local or approved site, a sign-in through the tour card or `credentials`), so an ordinary tour needs no part; each part is named with when to read it (only when a job waits on it, a report cites it, or the tour is of that kind). It opens with the hands-off rule: the agent never changes the app being toured, its data or its settings; never signs in to that app outside the recorder (no developer sign-in shortcut, no direct request or database query against the app's data); and never reads Sova's own records or other chats' tours, or anything but the app's own source; when something seems to need one of these, it asks the user. Next comes what to settle before writing (the scope, above), then how to explore: at most about ten reads of the app's source (its list of routes, the area's wording, a summary of its demo data), then one `look` (§app.tours/look), a job whose answer comes through `status`, which opens the named pages signed in at both sizes without pictures and lists what each shows; targets are taken only from that list, copied exactly, never guessed from styles or components; when the sign-in boxes are unknown, a first look with only the sign-in route lists that page as seen signed out. Then the rules behind most failed dry runs, in this order: each picture is one screen (desktop 1440×960, phone 390×844), and everything a view names, its marks, masks and every target it waits for, opens, fills or reveals, sits fully inside it at both sizes, with `reveal` to bring lower content into view; every target matches exactly one visible control, role and name first, and each view starts fresh; marks, views or steps are never deleted just to make a rehearsal pass, but fixed or moved into a reference view the agent reports; and the tour's own words are written in the reader's language while targets match the screen exactly, the agent asking the user once, before the first rehearsal, when the app shows another language. Then a six-line sign-in and site-approval list (a sign-in route that shows the password box signed out and the signed-in control after; the sign-in page is seen signed out, maybe in another language, its boxes named as it shows them by role or test id, and is never a view or a look page, since the look lists it signed out and a reference view describes it; the signed-in control is one every signed-in page shows (the app's home link in its header, say), named as it reads after sign-in, since the app may switch language then; the login in `credentials` or on the card; a sign-in notice acted on only after the job's status shows it still waiting; a job waiting on site approval sent to the user's Approve Site); the workflow in seven numbered steps (look, dry run, fix, record, inspect, check, show), the look's tour id reused for the dry run so the user signs in once, with real durations (a dry run 10 seconds to 3 minutes, a recording 3 to 12 minutes) and the waiting rule (status answers when the job finishes, fails, rests for the agent or needs the user, or after up to five minutes, so call it and wait, never sleep or poll in a loop, and calling it again is always safe); for an agent that can't see pictures, the only recording files it may read are the copies `inspect` writes into the chat's own working folder (`.sova-tour/<jobId>/`: each overview sheet, or the one capture asked for), handed to an authorized picture tool or the operator; a failure-to-fix table that gives, for each failure a report names, the change to make; the reference-view rule; and one worked example.

Scripts are declarative, versioned and strictly validated: stable chapter/step/view identities, page or reference views, semantic targets, safe actions, masks and explicit size availability. A target must resolve to exactly one visible control; an accessible role and name is preferred, text or test id can narrow it, and neither arbitrary JavaScript nor shell commands are accepted. A page view's `masks` may be left out, which means none. Unknown fields, duplicate or dangling ids, unsafe URLs, missing required pictures, oversized input and invalid geometry are refused with a concrete correction that names where the fault is: the step and view by position and id, and the field (for example "steps[12] is a string, not a step: a step is {id, chapter, title, summary, views}."). A text target, and a role target's name, match with the invisible direction marks U+200E, U+200F, U+202A–U+202E and U+2066–U+2069 ignored on both sides, so an amount a page wraps in isolate marks matches its plain text. A script may declare one sign-in, `signIn`: the sign-in page's route on the source, the username and password boxes, optionally an account box for a site that asks for an account or code before the username (a site's pre-filled code box, for example), the submit control, a control that is visible only once signed in, and optionally up to four exact origins the sign-in may send to (an identity provider's, for example), which count as declared sites. A page view whose route is the sign-in's route (its path, and its hash route too when the sign-in route names one, as the recorder matches it) is refused before anything runs, naming the view (`steps[i] "<step>" › views[j] "<view>" is the sign-in page; it is never pictured. The look lists it signed out; describe it in a reference view.`), since the recorder signs in there and would only load it again. The account, username and password boxes are named by accessible role or test id, never by text, so no login value can sit in a script. A script never carries an account, username, password or code: the agent passes a login it was given as `credentials`, per sign-in origin (an account exactly when the script declares an account box, a username, a password and optionally a one-time code), beside the script in the record request and never inside it. Credentials without an account for a script that declares an account box are refused before anything runs ("credentials for <origin> need an account: the script's signIn declares an account box."), and so are credentials carrying an account for a script that declares none. A managed Sova test copy's tour can't declare `signIn` ("A Sova test copy signs the recorder in by its own cookie; remove signIn."). The core includes one short worked example, introduced by what a look found, a valid script that signs in, reveals a lower control before marking it, names its mark by role, and keeps an unsafe state as reference text in three short paragraphs; tests run it, and the sign-in part's `signIn` examples, through the actual validators rather than treating them as plausible prose.

## §app.tours/requests — Requests and questions stay in chat

People request a tour in chat, describing what to explain, who it is for and what they should understand; there is no Make a Tour button or composer flyout. The agent asks for missing context before recording. Changes are requested the same way and produce a new recording rather than edits to published picture bytes.

Ask About This Step identifies the tour, edition, main step and named view in the host's controlled draft, preserves an existing draft, and focuses the composer. It never sends or steers by itself. A hand-off participant sees it only while allowed to write on that link and turn; normal holder, offer-lease, budget and attribution rules still govern Send. When Ask About This Step or Request More Coverage can't add its question, the composer's error line says why and the draft is left as it was: "Couldn't add the question. Try again." when the page couldn't re-check the conversation, and "It's no longer your turn, so the question wasn't added." when the turn has moved on; a draft too full keeps its own message. Participants can also request missing coverage, but a fresh recording waits for an operator or builder with access and never widens the participant's access. A host may offer Request More Coverage only when it supplies a turn-authorized controlled-draft callback; it preserves the existing draft, identifies the current tour, edition, step and view, and explains that recording waits for an authorized builder, without sending or granting access. Read-only owner/person previews and standalone tour links have no conversation or agent controls.

## §app.tours/recording — A visible, checked recording attempt

A recording request returns a durable job reference promptly. Asking for a job's status waits: the answer comes as soon as the job, since that chat last saw it (in a status, inspect, look, dry-run or record answer), came to rest where only the agent can move it on (checking, ready, failed, cancelled, interrupted), started waiting on the user (for a sign-in, a site approval or a test account), or, while waiting on the user, changed what it asks for or its failure; or after about 5 minutes with the job as it is. A job moving between its own working phases (queued, dry run, recording) has not changed for this purpose, and neither has a running job advancing through its views: neither ends the wait, so one job wakes the agent about once. A job that was already waiting on the user when the chat last saw it hasn't changed by still waiting, so asking again waits the full time; entering that state is a change, and leaving it for a working phase is not. A job resting where only the agent can move it on answers at once, and so does the first status after a server restart. Stopping the agent's turn ends the wait at once. Asking again is always safe. Its card shows real preparation, waiting or consent requirements, dry-run, desktop recording, phone recording and checking progress, including the current step/view/size and actual completed counts where applicable; it never invents a percentage or ETA. Queued cards show their place in line and Cancel. A recording waiting for a sign-in shows "Waiting for you to sign in" ("Waiting for a sign-in code" for a code) with the sign-in form and Cancel (§app.tours/sites). Failure, cancellation and interruption are explicit, with Retry where safe; server startup reconciles unfinished attempts rather than silently replaying interactions. The card offers Re-record only when the tour already has a checked edition, because Re-record repeats that edition's source. While a recording is in progress the card offers neither; a finished dry run waits in checking for the recording, and its card offers Cancel. Otherwise a tour with no checked edition yet (for example a first recording that failed, was interrupted or was cancelled) shows, in place of Re-record: "To record this tour again, ask the agent in this chat." Operator job reads, cancellation, exact-origin approval (one origin or Approve All), test-account submission and sign-in or code submission require the owning chat's current authorization; a sign-in or code answer carries exactly the fields the recording asked for, at most 16 KiB, and its reply never repeats or logs what was typed; a request cannot supply another caller's session, source scope or sandbox policy, and an unavailable trusted effective context refuses with a correction rather than guessing it.

Before taking pictures the agent runs the real navigation, target and action sequence without image output. Each view, in the dry run and in recording, starts from a fresh load of its page: before loading a view, the recorder leaves the previous one for a blank page that contacts nothing, so a view whose route differs from the last only by its fragment (`/#/a`, then `/#/b`) is loaded in full and its response checked like any other. Nothing an earlier view did in the page itself (its script state, its document, opened disclosures, typed drafts) carries over to the next; only the size's browser context, with its cookies and the site storage pages write, is shared. A view whose page answers without a successful response still fails the attempt. So a view that needs a disclosure open or a draft typed repeats that action itself. A leave-page ("leave this page?") prompt raised when the recorder leaves a view is accepted; every other dialog a page opens, an alert, confirm or prompt included, fails the attempt ("Blocked a dialog requiring user input during recording."). A request the previous view left in flight is cancelled when the recorder leaves it, and that cancellation alone never fails the attempt; a refused contact still does, including a GET sent while leaving, which goes through the same consent and identity checks. A write a page sends by itself (a fetch, XHR or beacon non-GET request, such as analytics or a "mark as seen" call), while a view is open or while the recorder is leaving it, is stopped quietly: it never reaches the site, it doesn't fail the attempt, and the job's report counts the writes stopped this way. On any site other than a managed Sova copy, a page's live connection (a WebSocket, such as a development server's live-reload socket) to an approved site opens and receives; anything the page sends on it is dropped and counted. It is admitted like any request the page makes, through the recording's proxy, only to an origin this tour declares or its page requested, each approved, and never after an open or fill. Anything the page sends includes its closing code and reason. A dropped send never reaches the site and doesn't fail the attempt; the job's report carries only the count, in the same count as the writes above. On every site, a page's connection to a `/ws/chat` path is refused before it opens and the attempt stops, as on a managed Sova copy below, so the recorder never opens a Sova chat. A form submission, and any request after an open or fill action, still fail the attempt ("Blocked POST request during read-only recording.", naming its method). Recording repeats those checks in fresh isolated contexts for each size, verifies the actual viewport and semantic readiness, waits for fonts and stable targets, and checks visibility and capture bounds. A view's page is captured once it has settled: its document keeps the same size and position, scrolled where the view's actions left it, for two frames running, waiting up to about 3 seconds. A mark or mask target must also hold still for two frames and sit fully inside the captured screen: one still moving then fails the attempt ("Target kept moving, so it couldn't be marked or captured."), and one outside the screen fails it ("Target is outside the captured screen.", naming where it is). The recorder never scrolls a mark or mask into view by itself; the script's actions do. The reveal action (`{op:"reveal", target}`) scrolls whichever scroll containers hold its target, an inner panel as well as the page, until the target is fully inside the screen, centred so it never sits flush with an edge, and waits for the page to settle; when a fixed or sticky bar covers the target there (or it is still outside), it tries once more scrolling only as far as needed, and if the bar still covers it the attempt fails ("Target is covered by "<name>", a fixed or sticky bar."). A pixel scroll (`{op:"scroll", x, y}`) still scrolls only the page itself. The page's settle also waits for every scroll inside it to stop, an inner panel's included. A mark's box is clamped to the captured screen (a box may end up to a quarter pixel past its edge and still count as inside), so every mark the recorder keeps fits the published picture, and the dry run builds and checks the same marks a recording would publish. A recording that fails for a reason the recorder didn't name still reads "Recording could not finish."; the server log then says what threw (its message only, never one that carries a sign-in detail). The recorder produces overview/contact sheets covering every step/view/size and labelled reference view. The agent inspects every overview cell, opens suspicious pictures closely, repairs failures and repeats. Inspecting also copies each picture it returns (the overview sheets, or the one capture asked for) into the chat's own working folder, as `.sova-tour/<job id>/<file>` (a folder that tells git to ignore it), and its answer lists those paths, so a model that can't see pictures can hand them to a picture helper; that copy is the one recording file the agent reads, and nothing else of the private store is copied. A folder already there as a link, or a file in the way, is never written through: the answer then names no copy. Checking refuses an overview sheet listed among `suspiciousCapturesReviewed`, naming that field and the sheet (the sheets count through `overviewReviewed`); a model that cannot inspect pictures needs an authorized visual checker or operator review before visual checking is complete.

A failure names the step, view, size, action and target, the zero or multiple matches and the nearby controls as ready-to-use targets (each with its role, or as text when it has no listed role, and how many visible controls it matches now), blocked requests/origins or out-of-bounds targets. A sign-in page that shows neither its signed-in control nor its password box lists the controls it does show the same way, at most 8. Nearby targets whose accessible name starts with or contains the requested name come first; an entry's name and text read with the spaces a reader sees between its parts (a link holding a heading and a paragraph is named "Practice groups Jumayah", never "Practice groupsJumayah"), and an entry that matches nothing as read is left out; and for a text target that matches nothing, the smallest visible element whose text contains the requested text comes first. When a view's marks at a size span more than one screen's height, its "Target is outside the captured screen." guidance says to split the view into two at that size and never to drop marks. A dry run keeps going after a target problem (no match, several matches, a target that kept moving, sat outside the screen or was covered, an action that isn't allowed on it) and reports every failing view in one answer: identical problems are grouped with the places they happened, and the list is capped, saying how many more there were. It still stops at once on a safety stop: a blocked write, socket, dialog, popup or download, a site that isn't approved or may not be contacted, and a sign-in that fails or no longer works. When two views in a row find none of their targets, it stops there ("Two views in a row found none of their targets, so the dry run stopped there."), since the page drawn there is not the one the script expects. A recording's capture still stops at its first problem. It never silently chooses a nearby control or exposes a private DOM dump. Fixed delays alone are not a successful readiness check.

Apart from the one sign-in below, recording sub-states never save, send, approve, create or submit. The closed action policy blocks form submission, mutation/non-GET requests, WebSocket sends (dropped quietly, as above, except on a managed Sova copy) and downloads; harmless-looking button captions are not authorization. Filling an autosaving control or a mutating GET is not assumed safe. Where a state cannot be exercised safely and faithfully, recording stops or the author uses clearly labelled reference text, never an invented screenshot. Signing in is separate from sub-state recording and authorizes no other write. When a script declares `signIn`, each size's browser signs in up front, before its first view: it opens the `signIn` route, carries on if the signed-in control is already visible (a session the tour already holds), and otherwise signs in with the login it holds, waiting for one on the card as below when it holds none, so a site that shows its sign-in form in place of any page is signed in before any view. The recorder waits up to 10 seconds there for the first of the signed-in control or the password box. When the password box shows first, the recorder waits for the page's network to go quiet and gives the signed-in control about 1.5 seconds more: if it shows, the page counts as signed in, so an app that draws its form while it checks a session it holds is never signed in again or typed into; the same settle applies before a view counts as signed out in place (below). When the sign-in boxes disappear before they are filled, a visible signed-in control counts as signed in, with nothing typed; otherwise the attempt stops as a sign-in failure that names the sign-in route and no step or view ("The sign-in page <route> stopped showing its sign-in boxes, so recording stopped."). If neither shows, nothing is typed, and the attempt stops ("The sign-in page showed neither its signed-in control nor its password box, so recording stopped.") unless that size's browser started from the session the tour already holds, in which case it carries on. In a browser that carried on that way, before a view's actions or its capture, its first view included, a visible declared password box with no signed-in control showing beside it stops the attempt with nothing typed ("The tour's held sign-in no longer works, so recording stopped. Record again to sign in."), and the tour forgets that held session (its login is kept), so the next attempt signs in up front again. A sign-in form shown on an origin that isn't one of the sign-in's origins is never typed into, and the attempt stops ("The sign-in page is on <origin>, which isn't one of this sign-in's origins."). That route is expected to show the signed-in control when already signed in, as most apps do by redirecting; a site that shows its form there anyway is signed in again in that size. The sign-in page is never captured: a stored script's page view whose own route is the sign-in route is never loaded or signed in for, and the attempt stops with the refusal the script check gives (`steps[i] "<step>" › views[j] "<view>" is the sign-in page; …`), rather than signing in and loading it again until the second sign-in's limit. The up-front sign-in counts as one of an attempt's two sign-ins at most, so when the route shows the signed-in control once signed in, a session the site ends mid-tour keeps exactly one silent re-sign-in, as below; a site whose route shows its form anyway may use that second sign-in up front, and a later mid-tour sign-out then fails the attempt. After that, a sign-in starts when a view's page lands on the script's `signIn` route on a sign-in origin, directly, by a redirect, or by the page sending itself there once its first loads settle (its path, and its hash route too when the route names one, such as `/#/login` on a hash-routed site), or, as below, when a view shows the sign-in's password box in place, so a session the site ends mid-tour is signed in again as below. A sign-out a site shows in place is caught too. In a size that signed in, or saw the signed-in control, up front: when a view's page, given up to 2 seconds, shows the declared password box before the signed-in control, and the signed-in control isn't visible beside it, the recorder never types into or captures it; it leaves the view, opens the `signIn` route and signs in there as up front, counting toward the attempt's two sign-ins, then loads the view fresh and runs its actions again. The check runs before the view's actions and again before its capture. If the route shows the signed-in control instead, the attempt stops with nothing typed ("This view shows the sign-in's password box while the site says the recorder is signed in, so recording stopped."). In a size that carried on from a held session without seeing the signed-in control, that same password box is never signed in again in place: it stops the attempt as a held sign-in that no longer works, as above. Any other password box, the declared one included when the signed-in control shows beside it, is never typed into and is captured masked like any other view. The recorder clears the declared account box, which a site may have filled in ahead, and types the account into it, then types the username and password into the declared boxes, all with real input events, and clicks the declared submit control. That click opens the only write exception, once per sign-in: one submit event of the form holding the password box and at most four non-GET requests to the sign-in origins, still through consent and source checks, closing when the signed-in control is visible or after 15 seconds; a page's own script sending the login (a fetch-submitted form) is covered. Accepted residual: other writes the page sends to the sign-in origins inside that window, analytics for example, use up the same four and reach the site. Nothing is captured during a sign-in, and the view's page then loads fresh. Wrong details make one attempt and fail it ("The sign-in didn't work with those details, so recording stopped. Check them and record again."), never retried, and the tour forgets that login. Wrong details are told apart from a signed-in control that never showed: when the signed-in control hasn't shown 15 seconds after the submit, and no code box or human check appeared, the details count as wrong only while the page still shows the password box on the sign-in route (or beside a visible alert); when the password box is gone or the page has left the sign-in route, the attempt stops instead ("Signed in, but the signed-in control (signIn.signedIn) never showed, so recording stopped."), with guidance to choose a control every signed-in page shows, named as it reads after sign-in (the app's language may differ from the sign-in page's), and the page it landed on's controls as ready-to-use targets (nearby); the tour keeps that login, so the next attempt signs in with it without asking, and holds no session from it; a page asking for a one-time code asks for it on the card and continues; a "prove you're human" check stops the attempt ("This site asks to prove you're human, so recording stopped. Tell the user, or use reference text."). The size's browser context stays signed in for the rest of the attempt, and later attempts of the same tour start signed in (§app.tours/sites); when a site ends that session the recorder signs in again once, silently, from the details it holds; if the site signs it out again in the same attempt, the attempt fails ("The site signed the recorder out again, so recording stopped."). A failure whose words would carry a login value reads "Recording stopped on a page that shows a sign-in detail." instead. A sign-in failure's guidance names what the agent may correct in the script's `signIn`, and otherwise tells it to tell the user; it never suggests changing the app, its data or its settings, or signing in to the app any other way. A write to a managed Sova copy is never stopped quietly: it still aborts the attempt. Before every capture the recorder burns opaque boxes over every visible password box, the declared account and username boxes and any box marked as a username, into the only stored picture bytes; nothing else is hidden beyond the tour's own masks. The safe action subset opens only native details summaries or explicit non-submit disclosure buttons with expanded state and a valid controlled region. Filling changes only a native text control's local draft value, without application input/change events; it is never presented as an application-accepted edit. After an open or fill, all network requests, including GETs, are refused, so a state that depends on that network activity needs clearly labelled reference text rather than a bypass.

One source has a narrow exception: a managed hermetic Sova test copy verified for this attempt, by the same check that admits its install token (§app.tours/sites). For that copy only, the recorder lets the page open `/ws/watch` on that origin, with only the query keys `path`, `feed` (sessions only), `tail`, `wire`, `have` and `claude`; server-to-client frames pass, and any client-to-server frame on any socket aborts the attempt with nothing published. The chat socket (`/ws/chat`) is refused, because opening it starts a chat process on the copy, and the attempt stops. Its failure report names the step and view and says: "this page opens a live chat; record it as reference text or choose an idle view". The author then records again with that view as reference text. Every non-GET request to the copy aborts the attempt too; the recorder's sign-in is a cookie Sova sets, not a request. Such a copy's sign-in stays that cookie: its tour declares no `signIn`, and every non-GET to it still aborts. Every other site keeps today's fail-closed blocking, apart from the sign-in above. The test copy's server guards the same line itself (§app.access/gate), and the interface has no special tour mode. A page's live connection to any exact origin that has answered as a Sova (a response marked as coming from a Sova server) in the same size's browser session is refused before contact, unless it is a verified managed copy's `/ws/watch`; a Sova server that never answered as one in that session still refuses the recorder's socket itself, because a socket needs a sign-in the recorder never has.

## §app.tours/look — Look at the app before the first rehearsal

Before its first dry run the agent can ask the recorder to look at the app, with `record_tour` `look`: the tour's source, its `sites` and `signIn` when known (or, before the sign-in is known, only the sign-in page's route as `signInRoute`), an optional tour id and login (`credentials`, as for a dry run), and up to 10 pages, each a route with optional actions per size. A look is a queued job like a dry run, under the same site approval, sandbox, sign-in card and network rules: only GET requests, a page's own writes stopped, and no form submission, socket send, dialog, popup or download except the one declared sign-in. It takes no pictures and keeps nothing from the pages but its answer.

When the request names a sign-in route, the look first opens that page in a fresh signed-out browser at desktop size, types nothing, and lists its controls, so the agent writes `signIn` from what the page shows rather than guessing. It then signs in as a dry run does (from the tour's held sign-in, the request's credentials or the card) and opens each page at desktop and at phone size, running its actions. For each page and size it lists up to 40 visible controls in page order (headings, links, buttons, fields and other named roles), each as a ready-to-use target (role and name; a test id for a box with no name; or its text when it has no listed role) with how many visible controls that target matches, whether it sits fully on the first screen, and its top and height on the page in pixels; and up to 40 links to other pages of the same origin as routes, hash routes included. A page whose route is the sign-in route (`signIn.route` or `signInRoute`, matched as the recorder matches it: its path, and its hash route when that route names one) is refused before the look runs (`pages[i] is the sign-in page; it is never pictured. The look lists it signed out; leave it out of pages.`). A page whose actions or load fail lists that problem, with nearby targets for a target that failed, and the look goes on to the next page; a safety stop or a sign-in failure stops it as it stops a dry run.

The look uses the tour id the request gives or creates one, holds its sign-in under that id exactly as a dry run does, and its answer says to reuse that id for the dry run, so the dry run starts from the held sign-in and no second sign-in card appears. A finished look rests in checking with its answer, and can't be recorded. The tool's description and the guide name the look before the first dry run.

## §app.tours/sites — Site consent and test accounts

A tour can explain any site that the chat is permitted to reach, but the operator approves each new exact HTTP(S) origin once on this installation: scheme, host and effective port, including loopback. The project's own verified running copies need no separate site prompt. Consent is remembered and revocable. The operator can revoke a site approval and remove a stored test account from the tour card of a chat that uses them: Revoke Site forgets that exact origin's approval for this whole installation, so the next recording that needs it asks again, and Remove Account deletes the stored account for that exact origin, so the next recording that needs it waits for a test account. Both live in the card's Sites and Test Accounts section, shown when any site the tour uses is approved or has a test account, under the caption "Approvals and test accounts apply to every tour on this computer. A recording that needs one again asks again." Remove Account asks first: "Remove this test account? You'll need to enter its password again." Remove Account's confirmation offers Remove Account and Cancel. Revoke Site asks nothing, but while a recording of that tour is running its button reads "Revoke Site and Stop Recording" instead of "Revoke Site". Both are operator actions on the owning chat: a deleted chat or another chat's request answers not found before anything is read or changed, and an origin that chat's tour doesn't use is refused with nothing changed. A recording already running rechecks consent at every contact, so a revoked origin stops it at its next contact; a removed account changes only later recordings. A recheck "at a contact" here means a check of consent, sandbox scope and the source's identity that started no earlier than that contact; contacts that arrive together may share one such check. The preflight names all declared sites, the purpose and the test-account or sign-in requirement. When a recording waits for several origins, the card's Approve All approves every origin it lists in one action, exactly those and only while they are still the ones the recording waits for. A recorded page's speculative loads never reach any site this tour wasn't approved for: no speculation-rules prefetch or prerender, whether the page declares it in its markup, a response header or a script, sends a request to such an origin. Every connection the recording browser opens, speculative or not, goes through the recording's own proxy, which admits only origins this tour declares (its source, its listed `sites` and its test-account origin) or that its page requested through the recorder's checked requests, each only while approved; anything else is refused before contact. A declared or requested origin whose approval is withdrawn, or whose contact finds the chat's sandbox scope changed or the tour past its limit of 64 different sites ("This tour contacts too many different sites."), stops the attempt at its next contact, through the proxy too. Every recording attempt runs that proxy, with the sandbox On or Off. With the sandbox On, the chat's sandbox proxy carries the recording as before, and for that attempt it also admits only this tour's declared or requested origins, each only while approved, deciding before any lookup or connection; the chat's own allowlist alone is not enough. With it Off, the recording's own proxy applies that rule to exact origins (scheme, host and port) and admits nothing else, where a project tour's own verified running copy counts as declared and approved and is admitted only at the exact endpoint the source-identity check resolved, rechecked at every contact, and loopback is not exempt: no connection bypasses the proxy. The recording browser's own background requests (its update and account checks, for example) go through the same proxy and are refused unless their origin passes the same rule. If the proxy cannot start, the attempt fails before the browser launches ("Recording couldn't start its network guard, so nothing ran."), and if it stops mid-attempt the attempt stops; it never runs with a direct connection. As a second layer the recorder turns speculation rules off in the recording browser and removes any speculation-rules script a page declares or injects; rules sent in a response header are not stripped, and the proxy alone covers them. This is not a promise that an approved origin receives no speculative request. The recording browser also runs with DNS prefetch, preconnect and background networking turned off. On the browser Sova's tests ran with, navigation prediction from a link, preconnect, DNS prefetch and prerender could not be made to contact anything even without those switches, so the tests cannot tell a working switch from a broken one and report those cases as skipped. For them the switches are a precaution, not a proven guarantee; the proxy still stands between them and any unapproved site. Running the proxy with the sandbox Off changes neither the public-origin attestation nor Open This Page: both still follow the chat's sandbox state, as below. An undeclared subresource origin a page requests that isn't approved yet is paused before contact and requires consent; one that is already approved is admitted and counts as requested for the rest of that attempt only; the next attempt starts again from the declared origins. A popup is never recorded: opening one fails the attempt, whatever its origin. A redirect, of the page or of anything it loads, to an origin outside those the tour declares or its page requested fails the attempt, approved or not, naming that origin: "This page redirects to <origin>, which this tour didn't declare. Declare it in sites, or use reference text." A speculative load to such an origin is refused before contact. A declared origin that isn't approved yet pauses before the recording starts. Denying consent yields a concrete failure or reference-text choice, not an automatic retry. Consent is rechecked at launch and after policy changes and never overrides sandbox policy. A named site's approved origin is not permission to reach private addresses through DNS: inside the recording child, named hosts other than the explicit localhost path must resolve to public addresses before navigation, and each available actual response-server address is checked again. Loopback, link-local or private resolution or rebinding aborts the attempt with no new edition, explaining: "This site name points at this computer or a private network; use the managed running copy or its literal address." Explicit literal local destinations and localhost remain subject to exact-origin consent, managed-copy identity and the chat's sandbox; unrelated remote sites are not refused merely for sharing a local service's port. No host-server DNS preflight is performed for recording or viewing. DNS checks run inside the confined child, or, for a sandboxed chat, in its proxy, and only for allowlisted names. With the sandbox On the attempt's proxy checks a name against the allowlist before any lookup, refuses non-public results (loopback, link-local, private, carrier-grade NAT, unique-local and IPv4-mapped addresses) and rechecks the address it connects to. An edition recorded with the sandbox On carries no public-origin attestation, so it has no Open This Page control. Inside the recording child, a named origin that resolves only to public addresses receives a private record-time attestation. The attestation travels only with authorized private edition metadata, never in a public presentation projection, and is the only named-host eligibility evidence used for the owner Open control; it never authorizes additional recording contact. If an actual response address is unavailable, a sandbox-off attempt uses its child preflight decision; a sandbox-on proxy attempt whose proxy cannot establish a permitted resolution fails closed.

A tour can record signed in, with a test account or a real account. Form sign-in (a site's own sign-in page, declared as the script's `signIn`) takes a username and password (and an account first, when the script declares an account box), and a one-time code when the site asks for one, from the tour card or from the agent. When a recording reaches the sign-in page with no login for it, it waits in "needs sign-in": the card shows a sign-in form for that exact origin (Username and Password, with Account first when the script declares an account box, or One-Time Code), the chat is marked as needing you (§app.session-list/needs-you), and the chat's agent gets one short notice telling it to check the job's status first and, only if it still waits, point the user at the card; the notice names the tour, its job, the site and what's needed, never a secret. The notice is never queued behind a running turn: Sova sends it once the chat is idle, and only if that job is still waiting for that same sign-in, so a wait that ended first (answered, cancelled, failed, finished or expired) sends none. The notice shows in the thread as a "Tour sign-in" wake row, never as the user's message, and a chat Sova can't prompt (open in a terminal, for example) gets only the mark, and the notice isn't sent later. When the user answers a recording's sign-in or site approval (on the card or through its route) and the job continues, the chat gets one notice the same way, tagged like the sign-in notice and shown as the same wake row: it names the tour and its job, says the recording continued after the user answered, and tells the agent to call `record_tour` status, which waits. It goes at once to an idle chat, and is never queued or held: it is dropped if the chat is busy at the answer or starts working before it goes (a working chat calls status itself), or if the job no longer continues from that answer (it came to rest, such as a finished dry run in checking, a failure or a cancellation; it waits on the user again; or a later answer took its place). One notice per answer, never a secret. The card says: "What you type here stays in memory for this tour only, not in the chat or on disk. It's cleared when the recording ends, or after 1 hour." A login the user or an agent supplies in the record request is valid, used without asking, and kept the same way: such a login, and the signed-in browser state it produces (limited to the sign-in origins), is kept only in the server's memory, per tour: a look (§app.tours/look), the dry run and the recording of the same tour share it, so one tour signs in once. It is cleared when that tour's recording ends (ready, failed, cancelled or interrupted), when any of its jobs is cancelled, when the chat is deleted, when Sova restarts, and one hour after it was first given, whichever comes first (a recording still running or waiting for a sign-in then stops, "The sign-in expired after an hour. Record again.", and its signed-in browser closes); a one-time code typed on the card is used once and never kept, and one supplied in the request is kept only until its first use. It is never written to a job, script, attempt, edition, report, log, tool result or backup, and nothing returns it. A record request carrying a login value that also appears in what the tour would write is refused before the request writes anything ("A sign-in detail appears in the tour itself (a username that also appears in a route counts). Keep logins only in credentials."). Credentials supplied in the chat stay in that chat's own transcript, as anything said in the chat does; Sova never shows or copies them anywhere outside that chat's own transcript (and copies of the chat the user makes, such as a fork): every view of the tool call's arguments (its tool card while the call streams and afterwards, shared and hand-off views of the thread, exports) shows them as "[hidden]". A form login never answers an HTTP authentication request; that stays the test account below.

HTTP authentication uses only test accounts in an isolated operator-controlled setup. A test password may be stored once in protected host-local account state, never in the tour, script, manifest, chat history, screenshot or public projection. A stored test account belongs to one exact origin and is reused by later tours of that origin without another account prompt. A test account belongs to the site address; a different running copy on the same address uses it too. Storing another for that origin replaces its credentials in place under the same opaque account identity, rather than retaining a second copy. An explicitly requested account that is missing or belongs to another origin is refused, never silently replaced by a different account. The recorder never reuses the operator's ordinary browser, profile, cookies, extensions or existing CDP session.

Touring Sova itself is a primary use, and Sova is recorded only from a managed hermetic test copy. A source is a verified managed Sova test copy only when the running-copy identity check resolves it to a registered instance in slot 1 or higher whose service is Sova's own server (the service that adopts the live install in slot 0), with its own state directory `.agent` inside that checkout as a real directory. Only then may a recording see Sova answers, and only from that exact origin. Slot 0, the live runtime and any other Sova are refused: "Tours of Sova use a test copy; start one for this branch." A copy that can call a model is refused: "This test copy can call a model; remove its auth.json or record a copy without one." It can when its `auth.json` holds any credential, when its model catalogue (`models.json`) defines any API key, request headers or a non-boolean `authHeader`, at provider or model level (except that an API key whose effective base URL, its own or else its provider's, is loopback and which is a short literal placeholder of at most 16 characters, neither an environment reference nor a `!command`, such as Ollama's `"ollama"`, is not a credential; an empty key is none; any other key, and any headers entry, refuses; the shipped model catalogue passes, because copies are also where the operator chats with hermetic test sessions), or when its project-service definition sets a provider key variable in a service's environment. An empty `auth.json` (`{}`) is fine; the file merely existing is not refused, but either file that cannot be read as a plain, size-bounded JSON file (unreadable, oversize, unparsable, a directory) counts as credentials. A credentials file that is a link is read through only when it resolves inside the copy's own checkout (as a test copy's linked model catalogue does); a link that points anywhere else counts as credentials. Accepted limits of this check, covered instead by the permanent zero-provider test: a model login shared through the operator's own home directory (for example a Claude Code login), provider keys the copy inherits from Sova's own process environment or a service unit's environment, which Sova cannot read, and a loopback model daemon that itself reaches a paid or cloud account (for example an Ollama signed in to a cloud account). The check is defence in depth; the zero-provider test is the proof that recording triggers no model call. Accepted residual: a copy's first read of each session file counts as a changed summary line, so on a freshly started copy that already holds sessions, the recorder's first view of the session list can bring the automatic session-naming run forward. It only brings forward a run the copy's periodic sweep makes anyway, and any model call it makes still sits behind the credentials checks above; the managed copy used for the Sova end-to-end proof holds no sessions. A test copy holds made-up data, and its own install token is its test account: after those checks, at each attempt, the server reads it from `.agent/sova/auth-token` (no symlinks, size-bounded) and gives it to the recording browser only as that copy's own sign-in cookie for exactly that origin, before the first navigation. Nothing the recording writes or returns carries the token: no URL it opens, request body, script, job, report, edition, recording log, capture or model output. Considered, not an issue: the copy itself prints its own sign-in link (with the token) in its startup log, which the project-services logs verb returns. Managed copies are transient, loopback-only workspaces with made-up data, and the checkout's `.agent` token file is readable to the same agent anyway. Every recorder request carries `X-Sova-Tour-Recorder: 1`, so no Sova's silent local sign-in, unlock, token route or pairing hands the recorder an install's identity (§app.access/gate). Publication is refused when any answer carried `X-Sova-Server: sova`, unless the source is resolved again at checking as that same verified managed copy. The flag is kept in the private attempt, so it survives a restart. Waiting for consent, a test account or a sign-in is visible and does not occupy a recording slot indefinitely (§app.tours/resources).

## §app.tours/sandbox — A tour cannot bypass its chat's restrictions

The recording controller and browser obey the requesting chat or worker's effective sandbox, network allowlist, tracked-worktree scope and parent tightening. Site consent cannot open a destination the chat is blocked from reaching. When equivalent confinement cannot be established, recording refuses before browser navigation; it never disables the sandbox to make a local tour work.

The effective sandbox is the state the requesting chat's own tools run under, known from the chat's newest recorded sandbox entry and from the state reported by the chat process this server holds for it. A recording is confined whenever the chat's recorded or live sandbox state is On, and it never runs unconfined on a guess. When this server holds the chat's process, its live state applies, and On wins over either source. When it does not, a recorded On entry still runs the recording confined, but a recorded Off or no entry refuses: a recording never runs unconfined without a live chat process vouching for it. Recording never reads the sandbox policy's default to decide. A held chat whose runtime reports no sandbox state, or a worker without verified parent scope, also refuses. Every such refusal says to open the chat, then retry; it never asks the user to change the sandbox to make recording work. A chat whose sandbox is still turning on (the provisional entry, or the chat process reporting it) is On but not yet enforced, so recording refuses until the real state is recorded, saying to retry in a moment.

The browser is launched through the existing runtime-free session-policy seam under OS confinement, with a fresh private profile and pipe-based control, not an unconfined debugging listener. Proxy environment variables alone are not containment. Navigation, redirects, subresources, popups, WebSockets, DNS, IPv6, QUIC, WebRTC and loopback/proxy-bypass channels remain subject to the effective restrictions. Existing platform policy limitations still apply equally to the agent and recorder. A sandbox-on recording reaches only the sites the sandbox allows, plus this project's own running copies: for those, a per-attempt proxy exception, off by default, admits exactly the one host and port the source-identity check resolved, is rechecked at each contact and ends with the attempt. The recorder gains no other local-port exception. A sandbox-off recording runs through its own per-attempt proxy as well, admitting only origins this tour's script declares or its pages already requested through the recorder's checks, and only while approved, with no loopback bypass (§app.tours/sites); if that proxy cannot start, the attempt fails.

Release blocker b1 is demonstrated with the sandbox on and a listening loopback test server on a non-allowlisted port: a tour navigating there is refused and that server receives zero requests. The test observes the server's request count, not only an error string; redirect and subresource cases are checked as well.

## §app.tours/source-identity — Re-record the same running copy

A tour of a project's running copy remembers the host/project, canonical checkout identity, stable running-instance identity and service endpoint, not the address or reusable slot alone. It resolves the live endpoint for each record and re-record and checks current ownership immediately before and during capture. The observed generation is provenance, not permission to follow a port to another copy. The agent names a project source by its running copy alone, `{kind:"project", instanceId, serviceId, endpoint}`, as the project's running-copy status reports them; Sova derives the project id and the canonical checkout from its own instance registry and the chat's project, and stores the full identity with the tour. A request may still name `projectId` or `checkout`, but each must equal the derived value exactly, or the request is refused naming that field. A malformed source field is refused naming the field and what it expects (for example "source.projectId must be an id like prj_…, not a path; omit it and Sova fills it in."), never with a generic invalid-script error. Likewise a script with a top-level field it doesn't take is refused naming that field and the fields a script does take, saying that a view's fields (`route`, `sizes`, `actions`, `marks`, `masks`) belong on a view inside `steps`; a page view missing one of the fields every page view needs (`route`, `sizes`, `actions`, `marks`, `masks`) is refused naming its place and the field, for example "steps[1].views[0] is a page view and needs actions" (positions count from 0). Any other problem inside a step or view, an unknown field included, is not yet named and still gets the generic error.

If that copy or service is stopped, absent, foreign or of unknown ownership, Re-record refuses or offers an operator-confirmed start of that same copy. It never starts a convenient substitute, silently starts a service or falls back to the old address. Restarting the same instance can re-record after re-resolution; a mid-recording swap stops the attempt. A job whose copy is refused, at its launch-time resolve or at any contact during recording (stopped, swapped, taken over, no longer registered or declared, or no longer a recordable Sova copy), ends `failed` with that refusal's own message, never the generic "Recording could not finish.". A copy that changes mid-recording (its generation, owner, socket or process changed, a takeover or a reused process id) reads "This running copy changed during recording. Retry against the same copy after it is stable."; a stopped service or a port another process owns reads "The original service is stopped, or another process owns its port. Start this same copy before re-recording."; a copy no longer meant to run reads "This tour's original copy is not running. Start that copy before re-recording."; an unregistered one reads "This tour's original running copy is no longer registered here.". The guidance is always "Start this same running copy through project services, then retry. Recording never starts a substitute." On Linux, when the copy's ownership can't be verified because this host's process information can't be read, whether at resolve or at a contact during recording, the attempt stops as a refusal would, but says so instead of refusing: "Sova couldn't verify this running copy: this host's process information can't be read." with "Retry in a moment. Recording never continues against a copy it can't verify." A listener on the copy's port that none of the copy's own service processes holds (another user's process included), or nothing listening, is still refused. On Linux each contact re-verifies the exact listening socket and the start time of the process holding it. Accepted residual: elsewhere each contact uses the platform's port-owner lookup as before, and an unknown owner there is still refused.

Release blocker b2 records copy A, stops A, starts copy B on the same port and requests Re-record of A: it refuses or asks to start A and B receives zero requests. Stale instance identities, reused slots and mid-recording swaps are checked too. Declaring a managed running copy as an external site cannot bypass these checks: a loopback site origin whose effective port belongs to any checkout-service registry entry, including a stopped copy's reserved port, is refused with an instruction to use that project's checkout, instance and service identity. A loopback site origin (the unspecified addresses `0.0.0.0/8` and `::`, also in IPv4-mapped form, count as loopback here because they reach this machine) on this server's own listening port, on any registry instance's port (slot 0 and the adopted live install's port included) or on a live share-listener port is likewise refused before any connection is made; the check for a Sova answer during recording stays as a backstop (§app.tours/sites). Accepted residual: with the sandbox off, a named host that resolves to this machine cannot be refused before contact; there only that backstop applies. This is rechecked during recording so a newly managed collision stops the attempt before further contact. Nonmanaged loopback sites remain available with exact-origin consent and the same sandbox restrictions. External-site tours otherwise retain their approved exact-origin identity. Source identities and account references stay in authorized internal edition/script storage, never the reusable presentation manifest or outsider projection.

## §app.tours/editions — Only a complete checked edition is readable

Every presented edition is immutable, complete and checked, with a distinct edition identity, script digest, check record and complete asset inventory validated for membership, sizes and hashes. Every pictured page view has both desktop and phone captures by default; a view genuinely available at only one size carries an explicit availability label. A reference view is labelled explanatory text with no fabricated picture.

A re-record stages a replacement without changing the previous complete edition. Until the replacement passes all checks, the previous edition remains readable; failed, cancelled or interrupted attempts never replace it with a partial tour. Publication is atomic. A malformed or failed tool result shows a safe failure row, not a plausible finished card. Transcript rows retain only a bounded card projection and authorized references, not the full script, report or PNG bytes; full authoring input remains lazily accessible only to authorized readers.

## §app.tours/viewer — Read steps, choose views, continue anywhere

The viewer preserves the approved reading experience: desktop explanation in a side panel beside a large picture; phone explanation below the picture on a narrow screen, beside it when the screen is wide enough; chapters and a table of contents; Back and Next moving main steps; named chips choosing views within a step; short explanations and a few correctly positioned numbered callouts. Changing desktop/phone picture size does not silently change the selected main step or named view. Reference states are clearly labelled text, never simulated recordings.

A reference view (one explained in words, not pictured) shows no Desktop/Phone switch, because there is no picture to resize; the switch returns on the next view with pictures, keeping the size the reader picked. A page view that lacks one size keeps the switch, with its "Desktop view unavailable" or "Phone view unavailable" text. The reference text sits in a card centred in the picture area at a comfortable reading width (about 65 to 75 characters a line) with a reading line height, labelled "Explained in words · not pictured". The text reads exactly as the agent wrote it, never rearranged; a blank line starts a new paragraph.

The tour card in chat lists the tour's chapters under "In this tour": one chapter per line, its number in a fixed monospace column, its title, and the steps it covers right-aligned ("Step 3" or "Steps 1–2"), from the tour's own chapter-to-step mapping. Each line is a button that opens the viewer at that chapter's first step. On a card 600px wide or wider, more than 5 chapters sit in two columns; on a narrower card the list shows the first 4 and a "Show all N" control that reveals the rest. The list is a real list, its lines are at least 44px tall on a phone and show visible focus.

Continue remembers the operator's place server-side across desktop and phone using stable step/view identities. A new edition maps stable identities or explicitly resets progress rather than jumping accidentally. Public readers have independent progress; a resume-position link can carry their place to another device without making every reader of one share link overwrite the same mutable position.

The card and viewer are keyboard- and screen-reader-operable, preserve focus and readable contrast in both themes (the numbered callouts, target outlines and leaders drawn on a picture keep the same on-picture colours in either theme, because the recorded picture keeps its own colours), respect reduced motion and keep touch targets at least 44px. Long copy and callouts remain readable without widening the page or hiding navigation. The final Galaxy Z Fold 8 pass uses measured usable CSS viewports for cover and inner screens in portrait and landscape, not estimated panel pixels or a substituted phone. At those four measured configurations, layouts are compact and readable, with tighter spacing and slightly smaller type where helpful while retaining comfortable controls; matched before/after card and representative viewer screenshots document the result without device-specific global token changes.

Open This Page is offered only in the owning operator chat, for a recorded HTTP(S) route on an approved exact origin whose address is eligible for use away from the recording machine: a literal public IP, or a named origin carrying the recording child's private attestation that it resolved only to public addresses at record time. A named origin without that attestation stays hidden; the control never performs DNS, fetches or other network probes while viewing and does not claim current reachability. Routes with any URL fragment stay hidden, including ordinary anchors: the first version does not classify fragment contents as safe or claim general secret detection. The origin approval is sufficient, with no second destination-review step. Loopback, private-network, `.local`, `.internal` and managed running-copy addresses are hidden. A host may instead offer a managed copy's operator share URL only after resolving its source identity at click time; omitting managed-share opening support leaves the control hidden. The link opens a new tab with noopener and noreferrer, never account credentials or tokens. Standalone public tours, outsider hand-offs, owner pages and person previews expose no Open control, recorded origin, route or source. Viewing, refreshing, switching views and opening a shared conversation never trigger a recording.

## §app.tours/sharing — Review every picture before a pinned, expiring link

The operator can create an expiring, revocable standalone share link for a checked tour in the first version. The tour's sharing dialog offers Create Link and Send to a Hand-off as distinct destinations; neither viewing the dialog nor an agent's suggestion performs either action. Hand-off confirmation requires review of that exact edition and destination; a pre-detachment preview cannot authorize reattachment (§app.tours/handoffs). Before making the link or sending to a hand-off, the preview displays every approved picture and all text a reader sees (the tour's title and summary, chapter titles, step titles and summaries, view labels and notes, callouts and reference text), identifies the audience and selected edition, and requires review of that exact snapshot. Above the pictures the review says when the edition was recorded and its size: "Recorded {date and time} · {n} steps · {n} pictures" (singular "1 step", "1 picture"); it never shows the edition's internal id; Create Link and Send to a Hand-off stay disabled until it is reviewed. Privacy masks are burned into the only published picture bytes, not applied as removable CSS blur. Sharing a tour grants no access to the recorded application or its accounts. An edition recorded signed in through a form sign-in (§app.tours/sites), whether the login came from the card or was supplied by the user or an agent, including one that started signed in from an earlier attempt of the tour, stays in its chat: it can't be shared or sent to a hand-off. Its card shows "Recorded signed in. This tour stays in this chat." in place of Share; the server refuses every link preview, link creation, hand-off destination list, hand-off preview and binding for it ("This tour was recorded signed in, so it stays in its chat. It can't be shared or sent to a hand-off."), checking the edition as it is when it acts, and a public or hand-off read of such an edition answers missing 404. An edition recorded with a stored HTTP test account stays shareable as before, because that account is stored only after the owner ticks "This is a test account, not my personal account"; the managed Sova copy's recorder cookie never locks an edition.

Each link is pinned permanently to the reviewed immutable edition it was made from; a changed or re-recorded tour needs a new reviewed link. The public page is read-only and exposes only a field-by-field safe presentation projection with opaque handles. It exposes no authoring script, raw source identity/origin, internal session ids or paths, account data, staging report or credentials. No recorded origin, route, source or Open control is exposed to a public reader; the owning operator chat's approved-origin opening policy does not apply to shared projections.

The distinct `/t/<token>` family serves only that edition's authorized manifest and exact listed assets. Authority is stored by token hash with the existing protected kept-token conventions. Expiry, revocation, edition identity and membership are checked on every byte request and rechecked after asynchronous reads. Traversal, symlink escapes, guessed cross-session assets and operator ownership endpoints on the share listener are refused. Private no-store, no-referrer, nosniff and restrictive CSP headers apply. Gateway registration negotiates `t` support for the exact target so an older gateway cannot reject the entire snapshot and break existing hand-off or owner links. Tour-image requests have their own bounded rate bucket and byte caps: at most 240 picture requests per token per minute for standalone and hand-off links, and 120 for owner links, separate from ordinary page/manifest buckets and the common per-address edge limit. Current authorization and exact asset membership are checked before this bucket, so an unauthorized or guessed asset remains missing 404 rather than revealing whether the token's allowance is exhausted. An offline or partial hop never masquerades as a complete picture. Standalone tour links participate in the existing host-wide opt-in Log visitors setting (§mesh.public/visitor-log), off by default. While it is on, they use the same visit path as session-share (`/s/`) links, with one protected host-local visitor-identity line per visit and the same forwarded-address rules, file modes and privacy exclusions; public readers and model prompts never receive those identities. While it is off, tour visitor logging writes nothing. Anonymous reader positions remain unchanged and are never joined to visitor identity, whether logging is on or off.

## §app.tours/handoffs — Reviewed context travels with the conversation

A checked, operator-reviewed tour can be bound explicitly to an organization hand-off session as a neutral tour attachment, unless its edition was recorded signed in through a form sign-in, which stays in its chat (§app.tours/sharing), not a generic tool-result or arbitrary image passthrough. Only the operator's sharing-dialog confirmation binds it in the first version; there is no binding tool or agent binding path, although the agent may suggest a destination in prose. Send to a Hand-off lists the operator's open baton conversations grouped by organization, using each public title and current holder. Selecting one previews every picture and all accompanying text for that exact edition and destination before confirmation; a preview for another edition or destination cannot authorize binding. The tour card lists its attachments and lets the operator detach one. The operator can also detach a tour from their own view of the hand-off conversation, so a tour that outlives its deleted source chat can still be detached. Detaching there has the same immediate effect for every reader. From a peer it needs admin access. The hand-off link, owner page and person page, including the operator's previews of them, stay read-only. Detachment immediately removes its authority for every reader, including offer-cut, owner and person previews; guessed old handles answer missing 404 before tour file access. Current active-branch detachment applies even beyond a reader's visible cut, without exposing the later entry or granting new viewing. Detaching never deletes retained source or destination snapshot bytes from disk, but removes that destination snapshot from the next committed organization backup. Older Git history is not erased by detachment. Reattaching requires a fresh preview and operator confirmation for that exact edition and destination; a preview issued before detachment cannot authorize it. Everyone allowed to read that part of the conversation can see it. The model can present only checked editions already approved and bound to that session/project through scoped `show_tour`. When the model uses scoped `show_tour` for an attached tour, the same tour also appears at that point in the conversation for everyone allowed to read it there, with the attachment's reviewed title, summary and steps. It is re-checked on every view: detaching removes it there too, and a show naming a handle that isn't attached earlier in the reader's view shows nothing. Its context contains public tour explanation and opaque handles, not private sources or authoring scripts. Tour presentation is baseline hand-off context, separate from Draw, Interactive drawings and Read links switches; it grants no `record_tour`, shell, files, workers or arbitrary browsing.

The outsider viewer uses the same presentation-only tour reader with token-scoped asset access and permitted controls. Every read resolves current link access and the same active-branch, never-holder offer cut and wrap-up visibility as the filtered conversation; session ownership alone is insufficient. Revoked, stale, closed or expired links serve no tour bytes. A tour attached after an invitation's visibility cut is not retrievable through that invitation, even with a guessed handle. Ask About This Step only prefills the participant's controlled draft while their link can write and never sends; requests for more coverage wait for an authorized builder.

All public tour text receives the conversation's phrase-redaction rules, and the operator previews and approves every published picture because text redaction cannot inspect pixels. Person-page preview uses the same filtered attachment projection without recording a visit or granting write access. The organization's owner can read checked public tour attachments only within conversations and cuts already exposed by the owner-page filter, using current owner-link access plus the opaque conversation and tour handles. `/api/i/<token>/c/<conversation>/tours/<handle>` and its exact-edition asset reads are read-only and have no Ask control. A revoked or expired token, another conversation, an attachment outside the allowed cut, a cross-edition asset or a guessed asset answers the same missing 404 before any file read; asynchronous reads recheck access before returning bytes. No script, report, source identity or recorded site address is exposed. Merely importing the viewer grants no whole-session-share tour access; that projection still needs explicit authorization.

## §app.tours/storage — Keep the explanation as long as its chat

Tours and checked editions remain available as long as their owning or referencing chats. Archiving may revoke public access but never deletes pictures from a retained chat. Only an actual transcript deletion triggers tour cleanup, not ordinary archive, a dry run or a refused deletion. After a successful irreversible transcript unlink, deletion first revokes the source's standalone links and unused previews, then tombstones the runtime in the same synchronous turn before any await: new tour work is durably refused, and queued or active attempts are cancelled. It waits for real child cleanup to settle, then removes private scripts, staging, inspection receipts, jobs and source editions. Cleanup also removes only that source chat's recorded owner-position metadata and the independent reader/position metadata belonging to its removed standalone links; destination-owned hand-off positions and other chats' readers remain. A synchronous durable deleted-session barrier prevents new work, a late completion or a queued request from recreating them, including after runtime or server restart. An unreadable, corrupt or symlinked deletion marker fails closed rather than reopening recording permission. Link-revocation failure does not skip recording cancellation and actual cleanup settlement; source-edition removal still waits for settlement. Once the owning chat is gone, every source-tour route is durably indistinguishable missing 404 even if cleanup left files behind, and no new binding can be made from that source. Cleanup failure never turns a successful irreversible transcript deletion into a reported failure: it emits only a bounded secret-free diagnostic, with no private paths, credentials or link tokens. Startup and a cheap periodic sweep detect tour state whose owning chat is gone and retry residual cleanup; the missing-chat checks continue denying all access meanwhile. Access denial is not permission to destroy retained state: cleanup requires a confirmed absent owner or a concrete regular, contained deletion marker. Permission errors, unsafe containment, symlinks and uncertain headers or indexes remain unknown for destructive cleanup; they keep access denied but never erase retained tours merely because the check could not establish ownership or deletion. After trusted session-header identity proof, Sova keeps a durable private host-local birth-owner record of the session identity, canonical owning transcript file and its parent session root. This record never grants read access: source authorization still requires the current allowed roots and current identity checks. Without a concrete deletion marker, cleanup can confirm absence only when the recorded owning file is absent while the same remembered root is still trusted, visible, plain and readable and its safe identity is established. A missing or dropped root, missing or corrupt owner record, symlink, uncertain header or index, or uncertain root visibility remains unknown, never destructive absence. With no deletion marker, a chat's tours are cleaned only when its owner is confirmed absent on two sweeps at least a minute apart that see the same session folders. The first sweep after a start never cleans on absence alone, and a chat that reappears in between keeps its tours. In this first version, a chat moved by hand outside Sova's known folders is therefore treated as deleted. Each such cleanup is logged with one fixed line. A leftover whose deletion Sova itself recorded is finished on the first sweep. Validated transcript moves retain and update the owner record; only completed source cleanup removes it, not a root disappearing. Independently approved destination-owned hand-off snapshots remain readable. Installation-wide reusable origin approvals and test-account secrets are retained; deleting one chat does not erase shared operator state. Authorized state-root storage separates scripts, attempts, manifests, redacted captures, overviews and reports; owner routes validate session ownership and exact inventory membership and never serve arbitrary filenames.

Binding an edition to a hand-off creates a destination-owned checked snapshot, so deleting its source chat cannot break that conversation's explanation. Checked hand-off manifests, redacted pictures and conversation bindings travel in the organization's private workspace backup and restore with its conversations, with no read from the old recording host. Backup size may grow with those pictures, but an oversize snapshot is refused before attachment. Workspace ignore rules do not silently omit a currently attached checked tour: only the exact validated destination-public manifest and the picture inventory it lists may bypass those rules, with every path resolved by realpath beneath the organization workspace root and no symlinks. No directory glob, source/private artifact, script or report is force-staged. After a backup commit, every listed path is checked against the committed Git tree; any missing inventory path produces a clear organization backup warning rather than a claim that the backup is complete. Detachment keeps retained source and destination bytes on disk but excludes that snapshot from the next committed backup tree, not older Git history. Generated untracked tour artifacts alone do not make the organization backup dirty or repeatedly trigger no-op commits; tracked tour edits stay visible and validated, and a binding or detachment still changes the backed-up conversation transcript. Restoring does not resurrect public links: new links must be issued. Jobs, browser profiles, test-account state, origin approvals, credentials, share tokens, private birth-owner records and raw staging stay host-local and never travel in the organization repo. The source card's source-to-destination attachment index also stays host-local; it is a list/detach aid, not the portable destination conversation's attachment authority.

## §app.tours/resources — A few recordings at once, with visible limits

Sova runs a few recording attempts concurrently up to a small configurable limit, rather than unbounded browsers or a mandatory single-recording policy. Further requests enter a bounded durable queue with an accurate place in line, progress and Cancel. At most one attempt for the same tour runs at once. Oversized tours are refused with a useful splitting instruction before consuming unbounded resources.

Recording happens in short-lived lower-priority children using the already-installed Chrome or Chromium, never on the request loop and never by downloading a browser. A configured executable or supported installed-browser discovery is used; a missing browser gives a clear refusal. Children read the existing worker niceness setting and their browser descendants inherit it. Resource monitoring charges their measured process cost to the requesting session and worker, not to an unnamed server task.

Process time, memory, image bytes, IPC output and queue length are bounded. Cancel, crash and interruption reap the browser process tree and private temporary profile; the server alone writes finalized state-root assets. Waiting for approval or a test account does not hold a scarce recording slot. A recording waiting for a sign-in keeps its browser and its place in its attempt, with the attempt's time limit paused for as long as it waits (the wait itself has no limit), and frees its running slot. Recordings waiting for a sign-in have their own limit, equal to the concurrent-recording limit (2 by default): a recording that would wait for a sign-in beyond it is refused, with a message naming the recording or recordings already waiting, never left waiting silently. An answered recording continues at once, so the running recordings can exceed the concurrent limit by at most the number that were waiting for a sign-in. Startup reconciles persisted attempts with interruption made visible; Retry never silently replays prior interactions. A finished capture waiting for its explicit check holds no browser, so a restart keeps it awaiting that check. The check still re-validates the private attempt, its pictures and receipts, the chat's sandbox, the source identity and consent, exactly as before the restart, and nothing is captured again. Attempts that were queued, running, or waiting for consent, a test account or a sign-in are marked interrupted, and none is replayed; a restart forgets every sign-in it held. Performance claims require measured wall time, memory and stored bytes for a desktop-and-phone tour, not an invented estimate.
