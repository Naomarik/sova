# Promoting a draft

The procedure and every refusal code are in [DRAFTS.md](DRAFTS.md). Don't repeat them here. What the tool can't check for you:

- **Decide what was implemented yourself.** The tool does not verify meaning. Promote behavior and surface changes only after checking their promises against the implementation. Notes and sections may use doc-only evidence, and so may a behavior or surface the user agreed to that has no `code` yet (`agreed: {by, at}`, DRAFTS.md "Agreed, not built"): publishing an accepted decision records the decision, not that it has been built. Its build keeps `agreed` and adds the code with ordinary evidence. A change to a behavior's or surface's `embeds` or `core` field alone may use doc-only evidence too (DRAFTS.md "Field-only changes"; `about` belongs on notes, which take doc-only anyway): its `--verification` says what you read (for an embed, both passages and the code that renders it), bundled with any other change to that record it is refused (`doc-only-bundled`), and on an agreed record that maps code it is refused too (`doc-only-refused`). A go-ahead from the user is not permission to commit.
- **Order, once a commit is permitted.** Commit the code first. Then run `evidence --commit <rev>` against a commit whose blobs match the tree *now*. That's usually `HEAD`, which isn't necessarily the commit that first implemented it. Then promote. Then commit the claims on their own, by explicit path (`.sova/spec/manifest.json .sova/spec/claims/...`), never `-A`. Without commit permission, stop after verifying: pending evidence and an unpromoted draft are the expected end state; say so in the reply and never commit to obtain a revision.
- **Preflight.** `status <name>` shows no `conflict`, and each selected ID's evidence is `valid`. `check <name>` has no findings other than `requires-uninvestigated`. A clean preview isn't a guarantee: some refusals are computed only when no other refusal fires, and `lock-occupied`/`race`/`plan-changed` show up only on `--write`.
- **Selection.** Select with `--id`, and never use `--all` on a draft that mixes promoted and unpromoted work. Set `authority: accepted` on new or rewritten prose yourself (promote also accepts `migrated` on rewritten text, which is wrong). Put the implementation files in each record's `code`, not in `--path`.
- **Conflicts can't be hand-fixed**, because `base/` is immutable. A conflict is per declaration: edits to different H2s of one file merge, while two different edits to the same declaration (or the same gap between declarations) stop, and the refusal names them. Either revert the conflicting declarations in the draft's `spec/` to their `base/` text and promote the rest, or start a new draft from current.
- **Keep the branch in step with master.** Merge master into the branch (`git merge master`) before promoting, so the draft and the promotion see master's current spec. Once evidence is recorded, never rebase, amend or squash that branch: the evidence commits must stay ancestors of what lands (`check` warns when one isn't, `promote` refuses it (`evidence-not-ancestor`), `census --changed` lists it (`orphanedEvidence`) and the census digest says so on the call that rewrote it, and `worktree merge` warns on unpromoted draft records). If you rebased anyway: while it is under way, `git rebase --abort`; once it finished, find the pre-rebase tip in `git reflog` and, with no uncommitted changes (commit them first), `git reset --hard <that tip>`. Then merge master in instead. If master's spec moved after you promoted, merge master in again; a promotion that then conflicts is re-applied from a new draft.
- **A spec conflict in a Git merge.** A `manifest.json` conflict alone is never spliced by hand or by a script, and never settled by taking a side before `merge-manifest` has run. Run `node "$core/sova-spec-draft.mjs" merge-manifest --root <project root> --json`, then again with `--write`, and stage the file yourself (or install it as Git's merge driver for that file: `core/README.md`; details in [DRAFTS.md](DRAFTS.md), "A manifest conflict in a Git merge"). With the `merge-claims` driver also configured for `claims/*.md` (DRAFTS.md, "A claims conflict in a Git merge"), a claim file conflicts only where the same declaration, or the gap beside it, changed on both sides; its markers hold both sides' prose for reading, never for splicing. When it refuses a key both sides changed differently (`manifest-conflict`), or any `claims/*.md` file conflicts, whether or not the driver already merged the manifest: take master's whole spec with `git checkout --no-overlay master -- .sova/spec/manifest.json .sova/spec/claims` (never `--ours` and never one file at a time: the merge driver may already have merged the manifest, and the branch's other claim files would then lack their records), commit the merge, promote the branch's drafts again with the same `--id`s (re-record evidence that `status` calls stale; re-apply a draft that is gone in a new draft from current), then commit the claims. That brings back the branch's non-conflicting records too; never drop them. The refusals (`manifest-conflict`, `spec-merge-conflict`, `current-invalid`) say the same words, with the project's default branch for master.
- **Nothing lands unaccounted.** A merge or promote shows the files it changes that no claim maps (`unmappedChanged`) and the draft records it leaves behind (`unpromotedDrafts`). Spec each such file whose change a user sees. Promote what shipped (always on the default branch, master or main); otherwise say in the reply why not. A `staleDrafts` line means other drafts here are old: run the `drafts` command it gives and tell the user which it reports `landed` (promote them) or suggests deleting; delete only with `prune --approved FILE --write` on a list the user approved. A successful check does not establish that unchanged prose still agrees with changed code.
- **Name what else it changes.** Name each foreign § in the promotion's `alsoChanges` in your reply as "Also updates §X: <what>".
- **Never edit `claims/` or `manifest.json` by hand.**
- **Commit message:** a subject naming what changed and the draft(s) it was promoted from; the records, grouped by what they now say; the commits verified against and what was actually driven or observed; then the gaps found while verifying that this change doesn't close, each one left for its own draft.
