# Merge round: check

Step 4 of each round. Paths here are relative to the playbook's folder (`references/` is beside `PLAYBOOK.md`).

4. **Check.** Attach the worktree (`worktree attach {path}`), then `round.mjs check <branch>`. It merges master in, runs every check (the unit tests with `pnpm test`, then every integration test with `pnpm test:int`), and leak-scans the commits landing would publish (those origin/master doesn't have). Conflicts are left for you: resolve the clear-cut ones and commit; otherwise ask the owner. A conflict in the spec (`.sova/spec/claims/*.md`, or a manifest `merge-manifest` refuses) is never yours: the check aborts that merge, leaving the worktree as it was, and prints a hand-back; send it to the owner, who merges master in and promotes its drafts again on top, then answers READY at the new head. On `needs: …`, tell an idle owner exactly what is missing. A step that fails in 0 s didn't run: read its log (AGENTS.md's Working rules cover `mise trust`, `agents/testing/overview.md` a symlinked `node_modules`).
   A test file that fails in the full run is run again on its own in the worktree, with the suite's runner, by the check itself. Passing alone, it is flaky: the check names it (`Flaky (…; not blocking)`) and it doesn't hold the branch; name it in the report. Failing alone too, it is run on master: failing there as well, it is pre-existing (`Pre-existing on master (not blocking)`), holds nothing, and goes in the report; passing on master, it is a new failure that holds the branch: tell the owner. A rerun that can't be told (timed out, the runner refused, master's checkout dirty or elsewhere) holds it too, with the reason. An extension suite that fails the same way on master is master's: say so.
   A leak-scan hit only in the branch's tree is the owner's to fix with a new commit. One in its history, or a commit a scrub cut out of master (`git log --oneline master..backstop/<what>`, then `git branch --contains <commit>`), means the branch can never merge: ask its owner to re-apply the change on a fresh branch from master.
   The owner's worktree is theirs. Uncommitted or untracked files stop the check: ask the owner to commit or clear them. Park them outside the repo only with the owner's OK, and put them back byte for byte before you are done. A symlinked `node_modules` is environment, not their files: you may rebuild it, and say so.
   Specs land with the code. Once every check passed, the check makes the branch's spec drafts official itself, on the branch, as one docs commit (trailer `Sova-Spec-Landing:`), and its verdict is `landable at` that commit: code and docs land in the same merge. A failing check writes nothing about the docs. Drafts that don't fit are a need (`docs don't fit: <§>, …`) with a hand-back for the owner: send it; the owner fixes its drafts (no commit needed) and answers READY again at the same head. Drafts changed since the user's Land It are a need too (`docs changed since Land It: <drafts>`): queue it again (`ask`), so Sova shows a Landing card with what changed. The spec check and census are never a need. Never promote a draft yourself in any other way, and never ask the user for a specs-only landing. The user's Merge Without Specs… at the head checked lands without them, naming the drafts left behind. A branch whose owner is gone is the user's call (step 1). `"specLanding": "off"` in the round's settings turns the docs step off: drafts not official then hold the branch (`docs not promoted: …`) and the owner promotes them on its branch.
   The also-update nudge never holds a landing either. Each area guide (`agents/**/overview.md` in the branch's tree) names, in its front-matter, the files it `watches` and the files to `alsoUpdate` with them. For each area whose watched files the branch changed while it changed none of that area's also-update files, the check prints `also update: touched <area> (…), not <file>`. Raise each one with the owner in the same message as any need, or on its own if the branch is landable. The owner answers "updated" (check again at the new head) or "not needed because …" (name it in the report). Don't wait on the answer to land a branch that is otherwise green.

Then land it: `references/land.md`.
