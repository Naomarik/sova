# Merge round: check

Step 4 of each round. Paths here are relative to the playbook's folder (`references/` is beside `PLAYBOOK.md`).

4. **Check.** Attach the worktree (`worktree attach {path}`), then `round.mjs check <branch>`. It merges master in, runs every check (the unit tests with `pnpm test`, then the integration tests a landing runs, `pnpm test:int -- --landing`: the everyday set plus each slow group the branch's changes trigger, never the tours; `agents/testing/overview.md`), and leak-scans the commits landing would publish (those origin/master doesn't have). Conflicts are left for you: resolve the clear-cut ones and commit; otherwise ask the owner. A conflict in the spec (`.sova/spec/claims/*.md`, or a manifest `merge-manifest` refuses) is never yours: the check aborts that merge, leaving the worktree as it was, and prints a hand-back; send it to the owner, who merges master in and promotes its drafts again on top, then commits, so the branch shows Ready to land again. On `needs: …`, tell an idle owner exactly what is missing. A step that fails in 0 s didn't run: read its log (AGENTS.md's Working rules cover `mise trust`, `agents/testing/overview.md` a symlinked `node_modules`).
   **What it ran.** The check names each test group it didn't run and why (`Skipped: Chat processes (no change to its areas)`, `Not run at landing: Tours`); put that in the report for the branch. When the user says to run everything for a branch, check it with `round.mjs check <branch> full`; when they say to run everything until they say otherwise, `round.mjs full on` (and `round.mjs full off` when they say so). The result then says `full run`. Releases run every group whatever landings skipped; there is no other catch-up run.
   **Wait for its real end.** The check prints `Expected: about …` and a `Time limit` before its first step. Either run it in the foreground with the call's timeout above that limit, or run `round.mjs check <branch> --background` (it prints the pid, the log and the expected time), set your wake-up to that expected time, and on waking run `round.mjs wait <branch>`, which blocks until the check ends and prints its digest (`--timeout <s>` below your call's timeout; on exit 1 it still runs: wait again). Never pick a wake-up time of your own. The only check durations you quote to the user are the ones the driver printed: the expected time, and what a rerun adds (below).
   A test file that fails in the run is run again on its own in the worktree, with the suite's runner, by the check itself, never by you: before each rerun it prints how much longer it adds (`Rerunning <file> on its own: adds about …`, and `Running <file> on master: …`). Passing alone, it is flaky: the check names it (`Flaky (…; not blocking)`) and it doesn't hold the branch; name it in the report. Failing alone too, it is run on master: failing there as well, it is pre-existing (`Pre-existing on master (not blocking)`), holds nothing, and goes in the report; passing on master, it is a new failure that holds the branch: tell the owner. A rerun that can't be told (timed out, the runner refused, master's checkout dirty or elsewhere) holds it too, with the reason. An extension suite that fails the same way on master is master's: say so.
   A leak-scan hit only in the branch's tree is the owner's to fix with a new commit. One in its history, or a commit a scrub cut out of master (`git log --oneline master..backstop/<what>`, then `git branch --contains <commit>`), means the branch can never merge: ask its owner to re-apply the change on a fresh branch from master.
   The owner's worktree is theirs. Uncommitted or untracked files stop the check: ask the owner to commit or clear them. Park them outside the repo only with the owner's OK, and put them back byte for byte before you are done. A symlinked `node_modules` is environment, not their files: you may rebuild it, and say so.
   Specs land with the code. Sova already told the owner to promote its drafts on its branch before the branch reads Ready to land. The check prints its spec check, census and drafts' status; the spec check and census are never a need, but a draft that isn't official is (`docs not promoted: …`; the draft tool's one rule, the same Sova's readiness reads: a draft whose claims a later promoted draft on the branch reworded is official, one a catch-up merge overwrote with master's text isn't), with a hand-back for the owner: send it. The owner promotes on its own branch, under the user's go-ahead, and its new head is queued again; never promote a draft yourself, and never ask the user for a specs-only landing. The one exception is the user's Merge Without Specs… at the head checked, or their word to land it without its specs (`round.mjs go <branch> without-specs`): the check names the drafts left behind and lands without them. A branch whose owner is gone is the user's call (step 1), and lands with its specs promoted or not at all.
   A `fixed waits: …` line lists new fixed waits over 2 s in the branch's changed tests: ask the owner to wait on a condition instead, in the same message as anything else; it never holds the landing.
   The also-update nudge never holds a landing either. Each area guide (`agents/**/overview.md` in the branch's tree) names, in its front-matter, the files it `watches` and the files to `alsoUpdate` with them. For each area whose watched files the branch changed while it changed none of that area's also-update files, the check prints `also update: touched <area> (…), not <file>`. Raise each one with the owner in the same message as any need, or on its own if the branch is landable. The owner answers "updated" (check again at the new head) or "not needed because …" (name it in the report). Don't wait on the answer to land a branch that is otherwise green.

Then land it: `references/land.md`.
