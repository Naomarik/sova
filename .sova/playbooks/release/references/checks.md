# Release: the pre-release checks

Step 3. Every check runs on the release commit, `"${sha}"` (the release branch's head), in the release worktree unless it says otherwise. A failure stops the release: fix it in its own commit on the release branch (or on master, then merge master in), make the release commit again if it changed, and run every check again. Record each command and its result for the report at step 4.

The unit tier, the everyday integration tests, the build and the typecheck are what the Merge round runs at every landing; a release adds the rest, and runs all of it unconditionally. That includes the slow integration test groups landings skip (`scripts/test-groups.mjs`: the tours never run at landing, and Chat processes only when a branch touches them): the release is the only place they run for every change, so a break they find may have landed since the last release.

1. **Typecheck and build.** `pnpm run typecheck`, `pnpm run build`. Also the release notes: `! grep -q RELEASE-DATE CHANGELOG.md && [ "$(grep -c '^## vX\.Y\.Z ' CHANGELOG.md)" -eq 1 ]` (the date is set and the entry appears once).
2. **Both test tiers.** `pnpm test`, then the whole `pnpm test:int`, every group included (never `--changed` or `--landing` here; it prints no `skipped group` line). A failing file: run it alone twice (`pnpm exec node scripts/run-tests.mjs <file>`); one that passes both times is flaky: name it in the report. One that fails the same way on master is master's: name it, and ask the user whether it holds the release.
3. **pi-config's extension tests**: every line of `pi-config/README.md`'s "Tests" block, from `pi-config/`, one at a time.
4. **The spec replay suite**, unconditionally (a release runs it whatever changed): from `pi-config/extensions/spec`, `SOVA_SPEC_REPLAY=1 node ../../../scripts/nice.mjs node --test tests/replay/*.test.mjs`. One replay at a time per machine: if a Merge round check may be running one, wait for it (`<state root>/locks/spec-replay.lock`).
5. **The site.** `cd site && pnpm install --frozen-lockfile && pnpm run build`. The build runs `scripts/check-docs-leaks.mjs`, which fails on any Docs page that names a spec ID or a source path. Then check the built landing: `grep -c '/stable/scripts/install.sh' dist/index.html` is at least 1, and `grep -c '/releases/tag/vX.Y.Z' dist/index.html` is at least 1.
6. **The spec check: no new findings.** With the trusted spec tools (AGENTS.md, "Product documentation"): `node "$core/sova-spec.mjs" check --root <release worktree> --json`. It exits 1 by design while behaviors wait on investigation; the gate is no finding that is new since the previous release. Compare with the same check on `vPREV`'s tree (`git archive vPREV | tar -x -C ~/.cache/sova-release-base`, then `--root ~/.cache/sova-release-base`). For v0.2.0, whose previous release predates the spec, the baseline was 143 `requires-uninvestigated` and 1 `code-missing` (`§chat.profiles/picker` naming the deleted `src/components/ProfilePlaybookCard.tsx`). A new finding: fix it through a spec draft, or ask the user.
7. **The leak scan** over everything this release publishes since the last one, from the main checkout: `node .sova/playbooks/merge-round/scripts/leak-scan.mjs --range vPREV.."${sha}"`. Exit 0 is clean; 1 lists hits (never printing the text): stop and ask the user, as the Merge round does (`.sova/playbooks/merge-round/references/traps.md`, "Scrub"); 2 means it can't check (no private-names settings): ask the user, never treat it as clean. Hits in commits already on GitHub are the user's call, not yours.
8. **The live server on the release commit.** With the Merge round paused (`references/prepare.md`), fast-forward the live tree's master, locally only: `git -C ~/webapps/sova merge --ff-only "${sha}"` (refused if master moved: merge master into the release branch and start the checks again). Nothing is pushed. Then restart the live server onto it by AGENTS.md's "Live server restart": the user's Apply on the Services tab, or the delayed `systemd-run` form as your turn's last call after a busy check, or ask the user. Busy sessions: ask the user. Afterwards `curl -s 127.0.0.1:4800/api/health`: `head` must be `"${sha}"` and `startedAt` after the restart. Use Sova for a few minutes (open a session, the Mesh page shows `Sova X.Y.Z`).

From step 8 until the push in `references/publish.md`, the live tree's master is ahead of GitHub with an unpublished release commit. Nobody pushes master in that window. If the user abandons the release, master must not go out as it is (it names a release GitHub doesn't have): `git revert` the release commit, and every commit that only the release carried, on master in the live tree before the Merge round resumes. Never reset a shared checkout.

Then **stop** (PLAYBOOK.md step 4).
