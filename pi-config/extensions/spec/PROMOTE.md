# Making drafts official

The procedure and every refusal code are in [DRAFTS.md](DRAFTS.md). Don't repeat them here.

**Your drafts land with your branch.** Where branches land through a landing step (Sova's merge queue, or the `worktree` tool's merge in any project), the landing makes every draft on the branch official, in one step, after its checks pass: `land --commit <branch head> --write` records each promise's evidence at that commit and promotes them all, all or nothing, and the landing commits that as one docs commit with the code. Nobody runs `evidence --commit`, `promote` or a docs commit by hand for it, and nothing is promoted after the landing. What the chat still owes each promise it changes is a short note on what it verified: `evidence <name> --id '<§id>' --by <you> --verification "<what you checked>" --note --write` (a promise without one holds the landing: `verification-missing`; one changed after its note: `verification-stale`). A promise labelled `authority: "candidate"` stays a draft. A clash at landing (the same promise changed on the default branch since) holds the branch and sends it back: `refresh <name> --write` moves the draft onto the current spec and marks each declaration both sides changed, for you to rewrite as one text; that needs no commit. It changes the drafts. Under Sova's merge queue the user's Land still covers them when the rewrite only makes them fit: answer the queue's request Fixed and say the drafts changed, and once the merge thread confirms it, the queue re-pins the drafts and lands them without a new Land. A new or changed promise, or an edit the user made, waits for the user's decision. A Land is never anyone's agreement to the promises: run `agree` only for a decision the user made in this chat. Where nothing lands branches (no Git, or work straight on the default branch), run `land --commit HEAD --write` once before your last commit and commit the spec files it names with the message it returns; without Git, promote by hand as below.

**The manual path** (no Git, or a project with no landing step). What the tool can't check for you:

- **Decide what was implemented yourself.** The tool does not verify meaning. Promote behavior and surface changes only after checking their promises against the implementation. Notes and sections may use doc-only evidence, and so may a behavior or surface the user agreed to that has no `code` yet (`agreed: {by, at, source}`, DRAFTS.md "Agreed, not built"): publishing an accepted decision records the decision, not that it has been built. Its build keeps `agreed` and adds the code with ordinary evidence. A promotion that changes an agreed record's numbers or backticked tokens but keeps its `agreed` carries an `agreed-kept-on-change` note: if the meaning changed, the go-ahead that changed it is a new agreement, so stamp it with `agree`. A change to a behavior's or surface's `embeds`, `core` or `notOwned` field alone may use doc-only evidence too (DRAFTS.md "Field-only changes"; `about` belongs on notes, which take doc-only anyway): its `--verification` says what you read (for an embed, both passages and the code that renders it), bundled with any other change to that record it is refused (`doc-only-bundled`), and on an agreed record that maps code it is refused too (`doc-only-refused`). The user's go-ahead to build or merge covers committing the docs with the code on its branch: never ask for it separately.
- **Agreed, stamped by `agree`.** For an agreed record with no `code`, `agree <name> --id '<§id>' --by <who> --verification <text> --write` (it takes `SPEC_AGREE_SOURCE`, which the runtime sets: omit `--source` then, since a different one is refused, `agree-source-mismatch`; without the variable, `--source <ref>` gives a reference, never a description, `agree-source-not-reference`; a `pi-session:<session id>#<entry id>` reference must resolve to a user message in pi's session files, `agree-source-unresolved` (at promotion, `agreed-source-unresolved`), while any other scheme, for a project whose go-ahead lives outside pi, is checked for its form only; a worker given no reference refuses any `--source`, `agree-source-not-given`; with neither it stamps nothing: `agree-unsourced`) (DRAFTS.md, "Agreed, not built") stamps the record and records its doc-only evidence, and promotes nothing: the record becomes official when its branch lands (`land`), with agree's `--verification` as its note. A record that maps code is only stamped: its build records its note.
- **Order (manual path).** Commit the code first. Then run `evidence --commit <rev>` against a commit whose blobs match the tree *now*. That's usually `HEAD`, which isn't necessarily the commit that first implemented it. Then promote. Then commit the claims on their own, by explicit path (`.sova/spec/manifest.json .sova/spec/claims/...`), never `-A`. Only where the user said not to commit, stop after verifying, leave evidence pending and say so; never commit to obtain a revision.
- **Preflight.** `status <name>` shows no `conflict`, and each selected ID's evidence is `valid`. `check <name>` has no findings other than `requires-uninvestigated`. A clean preview isn't a guarantee: some refusals are computed only when no other refusal fires, and `lock-occupied`/`race`/`plan-changed` show up only on `--write`.
- **Selection.** Select with `--id`, and never use `--all` on a draft that mixes promoted and unpromoted work. Set `authority: accepted` on new or rewritten prose yourself (promote also accepts `migrated` on rewritten text, which is wrong). Put the implementation files in each record's `code`, not in `--path`.
- **Conflicts can't be hand-fixed**, because `base/` is immutable. A conflict is per declaration: edits to different H2s of one file merge, while two different edits to the same declaration (or the same gap between declarations) stop, and the refusal names them. Run `refresh <name> --write`: it makes current the draft's base and writes each declaration both sides changed as one marked block in the draft's `spec/`; rewrite each block as one text (current's change and yours) and delete the marker lines (a block left is refused, `conflict-markers`). Or revert the conflicting declarations in the draft's `spec/` to their `base/` text and promote the rest, or start a new draft from current.
- **Keep the branch in step with master.** Merge master into the branch (`git merge master`) before promoting, so the draft and the promotion see master's current spec. On the manual path, once evidence is recorded, don't rebase, amend or squash that branch: the evidence commits must stay ancestors of what lands (`check` warns when one isn't, `promote` refuses it, `evidence-not-ancestor`). The landing records evidence again at the commit that lands, so a branch whose drafts land at its landing may be cleaned up freely. If master's spec moved after you promoted, merge master in again; a promotion that then conflicts is re-applied with `refresh`.
- **A spec conflict in a Git merge.** A `manifest.json` conflict alone is never spliced by hand or by a script, and never settled by taking a side before `merge-manifest` has run. Run `node "$core/sova-spec-draft.mjs" merge-manifest --root <project root> --json`, then again with `--write`, and stage the file yourself (or install it as Git's merge driver for that file: `core/README.md`; details in [DRAFTS.md](DRAFTS.md), "A manifest conflict in a Git merge"). With the `merge-claims` driver also configured for `claims/*.md` (DRAFTS.md, "A claims conflict in a Git merge"), a claim file conflicts only where the same declaration, or the gap beside it, changed on both sides; its markers hold both sides' prose for reading, never for splicing. When it refuses a key both sides changed differently (`manifest-conflict`), or any `claims/*.md` file conflicts, whether or not the driver already merged the manifest: take master's whole spec with `git checkout --no-overlay master -- .sova/spec/manifest.json .sova/spec/claims` (never `--ours` and never one file at a time: the merge driver may already have merged the manifest, and the branch's other claim files would then lack their records), commit the merge, promote the branch's drafts again with the same `--id`s (re-record evidence that `status` calls stale; re-apply a draft that is gone in a new draft from current), then commit the claims. That brings back the branch's non-conflicting records too; never drop them. The refusals (`manifest-conflict`, `spec-merge-conflict`, `current-invalid`) say the same words, with the project's default branch for master. In a spec whose records sit beside each claim file (format version 2, `core/README.md` "Record layouts"), a conflicted record file (`claims/**/*.json`) goes to `merge-manifest --write` first, like `manifest.json`, and the recovery is per area: take master's copy of only the areas that clashed, each claim file with its record file (`git checkout --no-overlay master -- <area>.md <area>.json`), commit the merge, and promote again only the branch's changes to those areas; the refusals then say that.
- **Nothing lands unaccounted.** A merge or promote shows the files it changes that no claim maps (`unmappedChanged`) and the draft records it leaves behind (`unpromotedDrafts`). Spec each such file whose change a user sees. A draft lands with the branch whose worktree holds it; a draft whose branch already landed without it lands with a fresh branch from the default branch (copy it into that worktree's `.sova/spec/drafts/`), never on the default branch itself; otherwise say in the reply why not. A `staleDrafts` line means other drafts here are old: run the `drafts` command it gives; promote the ones it reports `landed` as above, and tell the user which it suggests deleting. Delete only with `prune --official --write`, which deletes just the drafts the tool confirms are already official (`--from DIR` for copies kept outside the project, such as a merge queue's), or with `prune --approved FILE --write` on a list the user approved. A successful check does not establish that unchanged prose still agrees with changed code.
- **Name what else it changes.** Name each foreign § in the promotion's `alsoChanges` in your reply as "Also updates §X: <what>".
- **Never edit `claims/` or `manifest.json` by hand.**
- **Commit message** (manual path; `land` writes its own): a subject naming what changed and the draft(s) it was promoted from; the records, grouped by what they now say; the commits verified against and what was actually driven or observed; then the gaps found while verifying that this change doesn't close, each one left for its own draft.
